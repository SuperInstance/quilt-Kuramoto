**Repo:** `SuperInstance/eisenstein`
**Title:** `E12::norm()` panics in debug at extreme i32 inputs (i64 overflow)

---

## Reproduction

```toml
[dependencies]
eisenstein = { version = "0.3.1", default-features = false }
```

```rust
fn main() {
    println!("{}", eisenstein::E12::new(i32::MIN, i32::MAX).norm());
}
```

- `cargo run --release` → prints `13835058048839712769` (correct)
- `cargo run` → **panics**, overflow in `src/lib.rs:79`

## Why

`norm()` computes `a² − ab + b²` in `i64`:

```rust
let a = self.a as i64;
let b = self.b as i64;
let n = a * a - a * b + b * b;
n as u64
```

At `(i32::MIN, i32::MAX)` the true norm is `13_835_058_048_839_712_769`, past
`i64::MAX` (`9_223_372_036_854_775_807`). Release wraps and the wrapped `i64`
reinterprets to the correct `u64` — the right answer by luck, since the true
value does fit in `u64`. Debug builds trap the overflow first.

## Impact

Narrow but awkward: the same input gives an answer in release and a panic in
debug. For a crate described as "exact arithmetic for safety-critical systems",
a build-profile-dependent result is worth closing even if the inputs are
extreme. The doc comment's "fits in 24 bits for reasonable values" is an
informal expectation rather than an enforced bound — nothing rejects or
saturates larger inputs.

## Suggested fix

Widen to `i128` before the multiply-subtract:

```rust
pub fn norm(self) -> u64 {
    let a = self.a as i128;
    let b = self.b as i128;
    ((a * a - a * b + b * b) as u128) as u64
}
```

That is exact across the whole `i32` domain, since the maximum is ~1.38e19 and
`u64::MAX` is ~1.84e19. Alternatively return `u128`, or document and enforce a
coordinate bound.

A test at the four `i32` corners would pin it.
