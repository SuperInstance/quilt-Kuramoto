**Title:** VHW km/h→knots uses the km/h→m/s factor (5/18), under-reporting by ~49%

---

Found while surveying integer unit conversions across the fleet. Small fix, and
the path is live rather than dead code.

## Location

`firmware/src/nmea/nmea.c`, VHW (water speed) branch:

```c
} else if (nf >= 8 && f[6].len) {        /* field 7: km/h -> kn */
    if (nmea_fixed_to_u(f[6].p, f[6].len, &u) != 0) return -1;
    out->wspeed_ukn = (int32_t)((int64_t)u * 5 / 18);
}
```

## The issue

`5/18` is the km/h → **m/s** factor. km/h → knots is `1000/1852`, which reduces
to `250/463`.

| | factor | 20 km/h reads as |
|---|---|---|
| current | 5/18 ≈ 0.2778 | 5.56 kn |
| correct | 250/463 ≈ 0.5400 | 10.80 kn |

About a 49% under-read. The comment already says `km/h -> kn`, so this looks
like a transcription slip rather than a design choice.

## Impact

Only affects VHW sentences that omit the knots field and supply km/h — many
talkers populate both, so real-world exposure may be limited. The branch is
reachable and exercised by `firmware/host_nmea/main.c`.

## Suggested fix

```c
out->wspeed_ukn = (int32_t)((int64_t)u * 250 / 463);  /* km/h -> kn, 1000/1852 reduced */
```

Both `250/463` and `1000/1852` are exact in integers, so this keeps the parser's
float-free property. A regression vector in `host_nmea` pinning a known
km/h→kn pair would stop it recurring.
